# CSV 导入批量写入对照（2026-09-08）

基线为 0628e84 的处理器：每批使用 `.values(list_of_dicts)` 构造插入表达式。新实现保留原校验、冲突目标及返回 ID 计数，改用 `session.exec(statement, params=parameters)` 批量参数执行。

## 环境与方法

本机 WSL2/Docker，Python 3.14.7、PostgreSQL 18.6，独立 app_import_perf_test；一个数值测点的全有效 CSV，1,000 条一批，100,000 行源文件约 6.39 MiB。原二号线模拟采集继续运行，无并行本地测试、构建或恢复。不是生产服务器、真实工业文件或多用户并发测试。

默认内存跟踪会明显拖慢 Python 密集操作，因此运行耗时使用关闭 tracemalloc 的独立三次测量；内存另测，不混合两种口径。每版内部交替 sync/queued 顺序，但两个代码版本是先后测量，不是随机交叉试验。保留所有原始结果，存在机器背景波动。

## 无内存跟踪：后台任务完整处理时间

| 行数 | 基线三次（秒） | 新实现三次（秒） | 中位数变化 |
|---|---|---|---|
| 10,000 | 1.908 / 1.874 / 1.937 | 0.849 / 0.802 / 0.814 | 1.908 → 0.814 秒 |
| 100,000 | 18.783 / 29.754 / 18.272 | 6.774 / 6.927 / 7.268 | 18.783 → 6.927 秒 |

100,000 行的中位耗时降低约 63.1%，按行数/中位耗时计算约 5,324 → 14,436 行/秒（约 2.71 倍）。所有运行均核对实际入库行数。只描述本条件下的单批文件处理，不表述为平台整体性能、HTTP QPS、采集上限或生产 SLA。

## 单独内存测量

启用 tracemalloc 的 100,000 行后台任务，Python 分配峰值 28.06 → 24.32 MiB，降低约 13.3%；每版仅一次，需说明样本量限制。无跟踪的进程生命周期 RSS 最大值不是这个数字，两种内存指标不得混淆。
